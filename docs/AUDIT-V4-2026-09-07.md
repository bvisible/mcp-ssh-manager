**Audit de préparation de la V4 — 7 septembre 2026**

Périmètre : branche `v4`, commit `cfa2eacac4b323e1d00e5e2758a0adfeb84c00c0`, comparé à la version publiée 3.8.5. Audit du code, de la migration, du coffre, des approbations, de l’interface et de la distribution. Aucune publication ni modification du code applicatif ; ce rapport est le seul ajout au dépôt. Les essais ont utilisé des copies et configurations temporaires et des serveurs SSH fictifs locaux.

**Avis : une V4 intéressante, mais pas encore prête pour une publication stable.** La séparation moteur/interface, les tests de sécurité existants et la compatibilité du contrat MCP constituent une bonne base. Les défauts les plus importants apparaissent lors de l’adoption des nouveautés : modifier une configuration, activer une approbation, récupérer le coffre et enregistrer des données depuis le desktop. Un simple remplacement de la version npm, sans adoption du coffre, est beaucoup mieux couvert.

P1 signifie ici « à corriger avant la stable » ; P2 « défaut réel à traiter ou limitation à annoncer explicitement ». Une lecture du code et une reproduction ne sont pas présentées comme des preuves équivalentes.

**Ce qui est déjà rassurant**

- `npm test`, `npm run typecheck` et `npm run lint` passent sur une copie du commit audité, avec les dépendances locales et Node 25.8.2.
- Le build UI passe. Le fichier `dist/ui/app.js` reconstruit est identique à celui du dépôt sur cet environnement. Le bundle JavaScript mesure environ 902 ko, 257 ko compressés ; le warning Vite sur la taille n’est pas un blocage fonctionnel.
- Le scénario qui installe réellement npm 3.8.5 puis le tarball 4.0.0 passe ses **7 vérifications** : quatre serveurs visibles identiquement et `.env` inchangé.
- Un échange MCP réel avec les deux versions donne **37 outils identiques**, descriptions et schémas d’entrée compris.
- Les contrôles GitHub Tests, Code Quality et CodeQL sont verts sur le commit audité. La dernière répétition de build desktop réussie porte sur `f2bff6b`, antérieur au dernier correctif UI : il faudra reconstruire le commit final.
- Le control plane écoute sur `127.0.0.1`, utilise un token aléatoire, contrôle le Host et applique une CSP. Les secrets principaux sont chiffrés avec AES-GCM ; le renderer Electron est isolé et sans Node.
- Le paquet npm contient l’interface compilée et ses polices ; les versions du moteur, des manifests et du desktop sont alignées.

**Sécurité : deux problèmes plus anciens à ne pas emporter sans traitement**

1. **P1, inspection du code : la politique et la connexion résolvent différemment les noms.** La politique cherche le nom exact, alors que la connexion accepte aussi alias, correspondances partielles et domaines. La première peut donc obtenir une configuration nulle et autoriser, pendant que la seconde retrouve le serveur protégé. Le défaut de politique existe avant V4 ; la nouvelle approbation hérite du problème. Résoudre le serveur une seule fois puis transmettre sa configuration canonique à la politique, à l’approbation, au journal et à la connexion. La chaîne MCP complète de ce cas n’a pas été reproduite dans cet audit. Références : [politique](/Users/jeremy/mcp/mcp-ssh-manager/src/index.js:269), [connexion](/Users/jeremy/mcp/mcp-ssh-manager/src/index.js:573), [résolution des noms](/Users/jeremy/mcp/mcp-ssh-manager/src/server-aliases.js:46).

2. **P1, inspection du code : la vérification de clé SSH ne compare pas la clé présentée.** Le callback ignore son argument et accepte tous les chemins, y compris pour un hôte connu. Le message « Host key verified » n’atteste donc pas l’identité du serveur. Présent en 3.8.5. Comparer la clé réellement reçue aux clés connues, refuser les changements et prévoir un parcours explicite d’acceptation initiale. Aucun essai d’interception réseau n’a été réalisé. Référence : [hostVerifier](/Users/jeremy/mcp/mcp-ssh-manager/src/ssh-manager.js:115).

**Migration et récupération : les autres défauts confirmés**

- **P2 — Détection incohérente de l’ancienne configuration.** Le moteur recherche plusieurs emplacements ; l’interface de migration et `vault import` se basent sur `cwd/.env`. Avec uniquement le fichier utilisateur standard et un lancement depuis un autre dossier, l’API ne propose aucun serveur et le CLI échoue. Les overrides documentés ne suffisent pas à harmoniser ces chemins. Le CLI exclut aussi explicitement TOML malgré son aide « .env / TOML ». Partager une résolution unique entre tous les points d’entrée. Références : [migration UI](/Users/jeremy/mcp/mcp-ssh-manager/src/control-plane.js:1143), [import CLI](/Users/jeremy/mcp/mcp-ssh-manager/cli/vault.js:281), [résolution MCP](/Users/jeremy/mcp/mcp-ssh-manager/src/index.js:160).
- **P2 — Un coffre partiellement endommagé peut donner une sauvegarde incomplète annoncée comme réussie.** Reproduit avec deux secrets : seul le premier est vérifié ; une altération du second laisse `checkKey()` annoncer `ok:true, checked:2`. La sauvegarde puis la restauration gardent deux serveurs, mais un seul mot de passe. Vérifier toutes les valeurs et refuser un export incomplet. La lecture dégradée éventuellement utile au moteur doit être distincte de l’export de récupération. Références : [checkKey](/Users/jeremy/mcp/mcp-ssh-manager/src/secret-store.js:295), [lecture dégradée](/Users/jeremy/mcp/mcp-ssh-manager/src/secret-store.js:433), [sauvegarde](/Users/jeremy/mcp/mcp-ssh-manager/cli/vault.js:114).
- **P2 — La protection contre la perte de clé ne tient pas au deuxième essai.** Reproduit en supprimant uniquement la clé d’une fixture : le premier ajout est refusé, le suivant accepte la nouvelle clé tout en laissant les anciens secrets illisibles. Le contrôle dépend du fait que la clé vient juste d’être créée. Refuser durablement les écritures tant que la clé n’ouvre pas le coffre existant. Référence : [unlock](/Users/jeremy/mcp/mcp-ssh-manager/src/secret-store.js:328).

Ces deux défauts du coffre doivent être corrigés avant de recommander aux utilisateurs de supprimer leurs anciennes sources. Le retour à 3.8.5 reste simple tant que `.env`/TOML restent complets ; la V3 ne lit pas le coffre. Les nouveaux serveurs et modifications enregistrés uniquement dans le coffre demandent un export pour revenir en arrière.

**Approbations : rendre le contrat exact**

L’absence de control plane autorise actuellement une action pourtant configurée pour approbation. C’est un choix explicite, documenté, et non une découverte cachée : [code](/Users/jeremy/mcp/mcp-ssh-manager/src/index.js:303), [README](/Users/jeremy/mcp/mcp-ssh-manager/README.md:174). Pour une V4 centrée sur la supervision, je recommande de refuser lorsque l’approbation est activée et indisponible. Les installations sans approbation peuvent conserver le fonctionnement actuel. Un éventuel mode permissif doit être un choix visible et séparé.

Deux défauts supplémentaires :

- **P2, reproduit :** une URL HTTP malformée provoque une exception avant authentification et fait sortir le processus control plane, interrompant ses sessions. Le service est local, sans exposition réseau directe. Encadrer le parsing et retourner 400 ; installer une barrière d’erreur au routeur. [Parsing URL](/Users/jeremy/mcp/mcp-ssh-manager/src/control-plane.js:462).
- **P2, inspection :** `approval=always` ne passe pas par tous les outils. `ssh_download`, par exemple, rejoint directement la connexion et écrit localement. Centraliser la couverture ou documenter précisément les exemptions. [Téléchargement](/Users/jeremy/mcp/mcp-ssh-manager/src/index.js:933).

**Interface : conserver le style, améliorer la confiance et les parcours**

Essais navigateur sur le build produit, avec trois serveurs SSH fictifs : navigation, affichage des serveurs, contrôles de santé avec seuil dépassé, ouverture de terminal, navigateur de fichiers local/distant et refus d’une demande en attente. Le refus a vidé la file. Sur une seconde instance vide, les trois étapes de l’introduction se terminent et ne réapparaissent pas après rechargement. Aucune erreur JavaScript relevée pendant ces parcours. Ces essais ne remplacent pas un test sur infrastructure réelle ou une campagne complète d’accessibilité.

Mon avis visuel est positif : présentation sobre, typographie cohérente, hiérarchie lisible, terminal et fichiers intégrés sans encombrer la page. Je n’engagerais pas une refonte avant la sortie. Les améliorations les plus utiles seraient :

- **Montrer la protection effective sur chaque serveur :** mode, niveau d’approbation, source de configuration et confirmation que le moteur a pris le changement en compte. Une valeur enregistrée ne doit pas être confondue avec une protection active.
- **Afficher un état permanent du moteur :** connecté, reconnexion, arrêté ; erreurs et données périmées visibles. Le badge d’attente ne devrait pas continuer à sembler fiable après perte de communication.
- **Guider une migration complète :** découverte de toutes les sources, aperçu, import, validation d’une connexion, sauvegarde récupérable, test de restauration et consigne de retour arrière. Le desktop autonome a besoin d’un parcours de sauvegarde accessible sans installer ensuite le CLI.
- **Rendre les formulaires complets :** passphrase pour une clé chiffrée, bastion et règles du mode `restricted` dans des options avancées ; bouton « Tester la connexion ». L’interface expose actuellement `restricted` sans éditeur des règles correspondantes.
- **Clarifier les comptes supplémentaires :** ils peuvent être saisis dans le formulaire, mais aucun parcours de sélection/utilisation n’a été identifié dans la connexion actuelle. Finir cette fonction ou la retirer de la surface de la stable. Éviter une promesse visible sans effet vérifiable.
- **Faciliter le premier usage et le clavier :** sidebar déployée au premier lancement, champs associés à de vrais labels, focus contenu dans l’introduction, bouton final ouvrant directement l’ajout de serveur. Le wizard actuel est un ensemble de `div` et les labels du formulaire ne sont pas reliés aux inputs. Références : [wizard](/Users/jeremy/mcp/mcp-ssh-manager/ui/src/components/Wizard.tsx:79), [formulaire](/Users/jeremy/mcp/mcp-ssh-manager/ui/src/components/servers/ServerDialog.tsx:219).
- **Prévoir le nombre :** la vue liste existe et convient mieux à de nombreux serveurs ; filtres par groupe, protection et état seraient plus utiles avant la sortie qu’une nouvelle fonction de terminal. La capture à trois groupes montre beaucoup d’espace vide, mais ce point est une préférence de présentation.

Après stabilisation : recherche/export de l’activité, identification claire du client MCP à l’origine d’une commande, révocation des sessions et diagnostic de configuration en une commande. La priorité immédiate reste la fiabilité des fonctions déjà annoncées.

**Distribution et qualité : les derniers écarts**

- **Windows :** le dernier installateur de répétition est effectivement non signé : aucune table Authenticode, après vérification de sa correspondance SHA512 avec `latest.yml`. Le log « signing with signtool.exe » ne suffit pas. Ajouter signature et vérification du fichier final, ou annoncer explicitement une préversion Windows. [Build examiné](https://github.com/bvisible/mcp-ssh-manager/actions/runs/33553280274).
- **Linux :** annoncé dans le README, configuré dans electron-builder, mais absent de la matrice de publication et sans validation d’artefact identifiée. Construire et tester ou annoncer une disponibilité différée.
- **UI :** la CI racine ne compile pas l’UI et n’exécute pas les scripts navigateur. Le npm utilise le build committé, le desktop reconstruit. Ajouter build, contrôle de cohérence et tests fonctionnels bloquants. Plusieurs scripts navigateur affichent des échecs sans les convertir en code de sortie non nul : ils doivent devenir de véritables contrôles.
- **Dépendances :** au 7 septembre, audit du moteur avec `--omit=dev` : un package modéré (`qs`), aucun high/critical. Audits complets UI et desktop : zéro vulnérabilité signalée. La correction de `qs` est déjà proposée par [PR #79](https://github.com/bvisible/mcp-ssh-manager/pull/79). Ceci mesure les avis connus, pas la sécurité du code applicatif.
- **Build desktop :** utilise Node 20 alors que certains outils installés exigent au moins 22.12 ; le dernier build a réussi avec des warnings `EBADENGINE`. Aligner la version de build sur les exigences des outils, sans changer implicitement la compatibilité du moteur npm.
- **Paquet local :** `npm pack --dry-run` depuis le dossier de travail inclut `.claude/settings.local.json`, non suivi. Un checkout CI frais ne le contient pas ; une liste `files` explicite protégerait aussi les publications manuelles.
- **Auto-update :** aucune mise à jour installée de bout en bout n’a été validée dans cet audit. Vérifier la combinaison `app.relaunch()` et `quitAndInstall()`, la fermeture des sessions et la persistance des données. [Code](/Users/jeremy/mcp/mcp-ssh-manager/desktop/electron/main.js:475).
- **Homebrew :** son commit de mise à jour est poussé directement sur `main` après npm publish. Avec une branche protégée, il existe un risque d’échec tardif ; aucun push de test n’a été effectué. Préférer une PR dédiée. La CI Homebrew actuelle teste encore 3.8.5 et le wrapper Swift historique.

**Plan concret de publication**

2. Décider du comportement en absence d’interface pour `approval=always`, puis aligner moteur, UI, README et tests. Fixer le périmètre des plateformes réellement livrées.
3. Intégrer les changements récents de `main` et les corrections de dépendances. Réexécuter les vérifications sur le commit final. Le commit examiné n’est pas encore une consolidation finale de `main` et `v4`.
4. Publier d’abord une `4.0.0-rc.1` sur un canal npm **`next`**, et des artefacts desktop de préversion. Adapter le workflow avant cette étape : il utilise actuellement le tag npm implicite `latest` et met Homebrew à jour sans distinguer une RC. Ne pas promouvoir une RC automatiquement.
5. Valider sur les plateformes annoncées : installation neuve ; upgrade depuis 3.8.5 via `.env`, TOML et environnement MCP ; ajout/modification depuis l’UI pendant un MCP vivant ; bastion et clés chiffrées ; approbation/rejet/arrêt de l’interface ; restauration du coffre ; groupes ; redémarrage ; vraie mise à jour desktop ; retour arrière.
6. Construire et signer les fichiers définitifs, notariser/stapler sur Mac, vérifier les signatures après utilisation et contrôler les métadonnées de mise à jour. Publier ces mêmes fichiers validés.
7. Promouvoir la stable sur npm, GitHub, le registre MCP et Homebrew ; vérifier les versions effectivement disponibles. Finaliser notes V4, prérequis, disponibilité par plateforme, migration et rollback. Le changelog est actuellement daté du 31 août, et certaines pages disent encore « not released yet » ou mettent 3.8.5 en avant.

**Limites de l’assurance donnée**

Le test d’upgrade publié vérifie surtout `ssh_list_servers` et la conservation du `.env`. Certains champs de son fingerprint, comme `mode`, `platform` ou `proxyJump`, ne sont pas renvoyés par cet outil : comparer deux valeurs absentes ne valide pas leur préservation. Les secrets, connexions et mécanismes de rechargement nécessitent les tests additionnels proposés.

Pas de campagne sur serveurs de clients, pas d’interception réseau, pas d’audit cryptographique complet, pas de manipulation du trousseau personnel, pas de test interactif Windows/Linux ni de mise à jour desktop réelle. Les tests racine exécutés localement utilisent Node 25 ; la couverture des autres versions vient des résultats CI consultés. Les défauts notés « inspection » doivent recevoir des tests de régression lors de leur correction.

La version publique reste [3.8.5](https://github.com/bvisible/mcp-ssh-manager/releases/tag/v3.8.5). L’audit recommande de préparer les correctifs et une RC avant toute promotion stable ; il n’a effectué aucune publication.
